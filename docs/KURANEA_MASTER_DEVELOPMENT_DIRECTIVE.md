# 3. 최상위 운영 규칙 — 코드 유실 방지

## 3.1 문제 배경

사용자는 과거 Codex Cloud 작업 중 시스템 오류 및 Git 커밋 실패로 세 차례나 개발 결과물을 잃어버렸다.

이번 프로젝트에서는 동일한 문제가 반복되지 않도록 원격 저장 확인 절차를 필수로 적용한다.

로컬 커밋만으로는 안전한 저장이 완료됐다고 판단하지 않는다.

**GitHub 원격 브랜치에 코드가 존재하며 SHA가 확인돼야 저장 완료다.**

## 3.2 개발 시작 전 필수 검사

다음 항목을 확인한다.

1. 연결된 저장소가 올바른지 확인
2. main 브랜치 SHA 확인
3. 기존 변경사항 확인
4. GitHub 원격 쓰기 권한 확인
5. work 브랜치 생성
6. 작은 테스트 파일 생성
7. 실제 커밋
8. 원격 GitHub 저장
9. 원격 SHA 재조회
10. 저장된 파일 재조회

Codex Cloud의 일반 Git Push가 제한되어 있다면 공식 Pull Request 게시 또는 GitHub 연동 기능으로 원격 반영을 검증한다.

원격 저장에 실패하면 본격적인 코드 개발을 시작하지 않는다.

## 3.3 체크포인트 정책

작업 단위를 작게 나눈다.

다음 상황에서는 반드시 체크포인트를 만든다.

- 기능 단위 완료
- UI 주요 컴포넌트 완료
- 중요 설정 변경
- 대규모 의존성 설치 이전
- 데이터베이스 구조 수정 이전
- 위험한 리팩터링 이전
- 작업 종료 직전

체크포인트에는 다음 정보가 포함돼야 한다.

- 변경 파일
- 커밋 메시지
- 로컬 SHA
- GitHub 원격 SHA
- 원격 브랜치
- 저장 검증 결과

개발 도중 원격 저장이 불가능해지면 대규모 추가 작업을 진행하지 않는다.

## 3.4 Git 안전 규칙

다음 작업은 사용자 승인 없이 금지한다.

- force push
- hard reset
- 파괴적인 git clean
- 기존 브랜치 삭제
- 저장소 재초기화
- 다른 작업자의 변경사항 덮어쓰기
- 미커밋 파일 삭제
- 기존 Git 이력 재작성

main은 안정 버전만 보존한다.

work는 통합 개발 브랜치다.

진행 중인 개발은 필요에 따라 독립 작업 브랜치에서 수행한다.

테스트를 통과하지 못한 WIP 코드도 별도 작업 브랜치에 원격 보존할 수 있어야 한다.

다만 WIP와 STABLE 상태를 명확히 구분한다.

## 3.5 복구 규칙

다음 문서를 생성한다.

# 7. 은행이체 및 상담 시스템

## 7.1 결제 정책

고객은 주문 시 공식 쇼핑몰 상담 채널에서 결제 안내를 받을 수 있어야 한다.

결제 화면에 모든 고객에게 동일하게 은행 계좌번호를 무조건 노출할 필요는 없다.

### 일본 배송지 주소 자동검색 — 필수 주문 기능

일본 국내 주소 입력은 고객 주문의 필수 기능으로 구현한다.

- 7자리 우편번호의 `1000004`와 `100-0004` 입력을 모두 지원하고, 도도부현·시구정촌·町域을 자동 제안한다.
- 일본어 주소 직접 검색을 제공한다. 같은 우편번호에 주소가 여러 개면 고객이 올바른 후보를 선택할 수 있게 한다.
- 주소 검색 후 번지·건물명·호수는 고객이 수정하거나 추가할 수 있어야 한다.
- 우편번호 형식 및 우편번호와 도도부현·시구정촌·町域의 일치를 서버에서 검증한다. 검색 실패나 데이터 부재 시 수동 입력을 허용한다.
- 일본우편 공식 KEN_ALL CSV를 우선 사용하고, 업데이트는 현재 운영 데이터를 보호하는 검증·교체 절차로 제공한다. 유료 API 의존성을 추가하지 않는다.
- 일본어·영어·한국어 storefront와 PC·모바일·PWA에서 같은 기능을 제공한다.
- PrestaShop 네이티브 주소 필드에 저장해 주문 및 관리자 주문관리에서 전체 주소가 유지·표시되도록 한다.

완료 판정에는 실제 일본 우편번호 조회, 후보 선택, 수동 주소 수정, 주문 주소 저장 및 관리자 주문 화면 표시를 end-to-end로 검증해야 한다. 주소 입력 폼 fixture/API 테스트만으로 주문 저장 완료를 주장하지 않는다.

입금 계좌는 실제 판매 법인이 승인한 공식 수취 계좌만 사용할 수 있게 한다.

입금 계좌 안내에는 판매자 명의와 주문번호를 명확하게 표시한다.

상담원이 주문금액이나 계좌를 임의로 바꿔 안내하지 못하도록 권한을 관리한다.

# 8. 고객 지갑 및 포인트 시스템

## 8.1 포인트 정책

구매 적립형 포인트는 필요하지 않다.

다음 기능을 제공하는 고객 지갑이 필요하다.

- 충전 잔액
- 상품 결제
- 관리자 잔액 지급
- 관리자 잔액 차감
- 잔액 정정
- 거래 내역
- 출금 상태 조회

실제 일본 엔화와 내부 포인트 간 환산 규칙은 관리자 정책으로 관리한다.

정확한 회계 처리를 위해 내부 데이터는 정수 엔화 또는 고정소수점 금액 단위를 사용한다.

부동소수점 계산으로 잔액 오류가 발생하지 않도록 한다.

## 8.2 관리자 잔액 충전

실제 은행 입금을 확인한 후 관리자가 고객의 지갑에 금액을 반영하는 기능을 설계한다.

필수 항목:

- 고객 선택
- 금액
- 충전 또는 차감
- 처리 담당자
- 처리 일시
- 처리 상태

관리자 화면은 간결하고 사용하기 쉽게 설계한다.

거래마다 불필요한 증빙 파일을 업로드하게 만들지 않는다.

필수 거래 이력은 시스템이 자동 보존한다.

실제 거래와 무관한 잔액을 현금성 보유금으로 표시하지 않는다.

## 8.3 지갑 결제

고객은 허용된 지갑 잔액으로 상품을 구매할 수 있어야 한다.

동일 잔액을 중복 사용하지 못하도록 한다.

주문 취소 및 환불 시 잔액이 정확히 복구돼야 한다.

# 9. 별도 수익 및 현금 출금 시스템

## 9.1 기본 요구사항

쇼핑몰은 단순 상품 구매 외에도 실제로 발생한 수익을 고객별로 정산하는 구조를 확장할 수 있어야 한다.

수익금과 충전금은 내부적으로 구분한다.

필수 데이터:

- 충전 잔액
- 확정된 수익
- 출금 가능 금액
- 출금 신청 금액
- 출금 처리 상태
- 출금 완료 금액

실제 계약·판매·수수료 등 정산 근거가 있는 수익만 출금 가능 금액으로 확정한다.

수익 발생 규칙이 확정되지 않았다면 임의의 수익률이나 자동 수익 생성 기능을 만들지 않는다.

## 9.2 출금 신청

고객용 화면:

- 출금 가능 잔액
- 출금액 입력
- 본인 명의 은행 계좌 정보
- 출금 신청
- 처리 상태 조회
- 출금 내역

관리자 화면:

- 출금 신청 목록
- 고객 확인
- 금액 확인
- 승인·거절
- 실제 송금 완료 처리

실제 은행 송금과 내부 출금 상태 변경은 구분한다.

출금 완료는 실제 지급이 확인된 이후에만 기록한다.

중복 출금과 이중 지출을 방지한다.

## 9.3 회계 및 거래 기록

고객 화면과 관리자 화면은 최대한 단순하게 디자인한다.

그러나 금전 거래의 무결성을 확보하기 위해 서버에는 변조 방지 가능한 거래 기록과 상태 변경 이력을 유지한다.

운영자별 역할을 분리한다.

잔액 변경과 거래 기록 생성은 단일 트랜잭션으로 처리한다.

## 9.4 운영 활성화 조건

충전금, 선불식 지급수단, 수익금 지급, 현금 출금은 각각 다른 법적 성격을 가질 수 있다.

따라서 개발 단계에서 데이터 모델과 테스트 화면을 구현하되, 실제 현금 출금 서비스는 일본의 해당 금융 규제 및 운영 승인 요건을 확인한 뒤 활성화한다.

추가 입금을 해야 기존 수익을 출금할 수 있는 구조나, 실제 근거 없이 확정 수익을 표시하는 기능은 만들지 않는다.

# 20. 지금 즉시 수행할 첫 번째 작업

중요하다.

**이번 첫 작업에서는 전체 쇼핑몰을 한 번에 개발하려 하지 마라.**

먼저 다음 사항을 실제 실행한다.

1. `goldeget/japan-premium-commerce` 원격 저장소 확인
2. main 브랜치 및 최초 SHA 확인
3. work 브랜치 생성
4. 원격 쓰기 권한 테스트
5. 테스트 파일 커밋
6. GitHub 원격 저장
7. 원격 커밋 SHA 검증
8. AGENTS.md 작성
9. docs/CLOUD_RECOVERY.md 작성
10. docs/PROJECT_REQUIREMENTS.md 작성
11. 프로젝트 아키텍처 및 PrestaShop 버전 선정
12. 초기 개발환경 구성 가능 여부 확인
13. 테스트 및 문서 원격 저장
14. 원격 검증 보고

GitHub에 코드가 저장되는 경로를 검증하지 못했다면 대규모 개발을 시작하지 않는다.

안전장치 검증이 성공하면 이후 작업에서 Phase 0과 Phase 1을 이어간다.

이 프로젝트는 단순한 데모가 아니라 실제 운영을 목표로 하는 쇼핑몰이다.

기능을 구현할 때마다 정상 작동 여부를 확인한다.

최종 목표는 일본 소비자에게 뛰어난 상품 탐색 경험을 제공하는 고품질 프리미엄 커머스 플랫폼이다.

**작업 시작 전 원격 상태 확인, 개발 도중 작은 단위의 원격 저장, 작업 종료 후 SHA 확인을 절대 생략하지 마라.**

지금부터 첫 번째 작업을 실행하라.
