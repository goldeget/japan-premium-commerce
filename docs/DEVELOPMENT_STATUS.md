기준일: 2026-10-21

작업 브랜치: `work`
마지막 기능 체크포인트 SHA: `ec7af91b66bdb31a36ea073957fdd8c7d428d334`

## 실행 기반

- PrestaShop 9.2.0, Hummingbird 2.1.2, MariaDB 10.11, Docker Compose를 사용한다.
- 로컬 실행 중인 PrestaShop과 MariaDB 컨테이너는 healthy이며 쇼핑몰은 `127.0.0.1:8080`에 바인딩돼 있다.
- `main`은 `ee02a3657448d563508687614a246e05ac61eecd` 상태로 보존한다.
- 이 Codex 환경에서 관측한 cloud environment spec revision은 2다. 요청된 revision 3이 현재 실행 환경에 적용됐다는 증거는 없다. 환경 설정은 변경하지 않았다.
- 호스트 작업공간은 약 194 MB 여유, inode 95% 사용 상태다. 기존 컨테이너·named volume은 보존하며 Docker 빌드, prune, 볼륨 초기화를 하지 않았다.

## 최근 작업

- JPY 설정을 신규 설치 및 기존 설치 부트스트랩에 연결했다. DB에서 JPY 활성·기본값, ja/en/ko 통화명을 확인했고 상품/주문 수는 각각 0건임을 읽기 전용 조회로 확인했다.
- 우편번호 테스트는 `1000004` 샘플뿐 아니라 CP932 파싱, 전각 입력, 복수 후보, 후보 선택, 네이티브 주소 필드 및 수동 건물명 매핑을 포함한다.
- 관리자 계약 테스트는 특정 로그인·번역 오버레이만 확인한다. 전체 관리자 한국어 수용 기준을 충족한다고 표시하지 않는다.
- CI 실패 진단 스크립트는 로그를 stdout·요약·artifact에 쓰기 전에 자격 증명 형태를 가리고, 이후 설치 단계의 실패에도 같은 수집기를 사용한다. 테스트용 민감 문자열을 실제 로그와 요약에서 제거하는 회귀 검사를 추가했다.

## 다음 우선순위

1. 인증된 GitHub Actions 상세 로그에 접근하거나 요약에 진단 내용을 노출해 새 설치 실패 원인을 확인하고, 격리된 빈 볼륨에서 PASS를 얻는다.
2. 공식 KEN_ALL 데이터의 실제 후보 조회와 native 주소/주문/관리자 주문 표시를 격리된 설치에서 검증한다.
3. 고객용 상품 상세·장바구니·주문 흐름과 관리자 한국어 범위를 확장한다.
4. 실제 기기 또는 이에 준하는 브라우저 설치 테스트로 PWA를 검증한다.
