# ORDENOWA 상품 발주·수당 포인트 관리자 안내

2026-10-29 구현 후보 기준이다. 현재 전용 모듈은 상품 안내, 고객 발주 요청, 수동 검토, 별도 수동 포인트 지급·연결 정정, 서비스 정책과 알림 처리를 구현한다. 발주 요청·포인트·알림의 기능별 격리 PHP/MariaDB 검사는 통과했으며, 동일 후보의 통합 화면·메일·재시작·복원 검증은 진행 중이다. 운영 공개, 실제 SMTP 수신 또는 실제 기기 Push 인수를 완료했다는 뜻은 아니다.

현재 제품 기준은 [최종 설계](superpowers/specs/2026-10-29-ordenowa-procurement-points-platform-design.md)다. 상품 발주 요청과 수당 포인트를 운영하며, 배송·반품·상품 환불·장바구니·결제·현금 환산·출금 신청은 현재 업무에 포함하지 않는다. 기존 상거래 기록과 코드는 보존한다.

## 관리자 계정과 권한

Back Office에서 해당 쇼핑몰 하나를 선택하고 담당자별 계정을 사용한다. 신규 모듈 메뉴는 한국어로 제공한다. 고객 기본 언어는 일본어이며 영어·한국어 화면과 알림을 지원한다. 네이티브 관리자 전체 번역과 실제 기기 접근성의 완료 여부는 별도 QA 결과로 확인한다.

| 메뉴 | 운영 업무 | 필요한 네이티브 권한 |
| --- | --- | --- |
| 상품 발주 안내 | 대상 회원·상품·옵션·수량을 안내하고 제출 전 회수 | READ, 등록 ADD, 회수 EDIT |
| 발주 요청 검토 | 미결 요청을 승인·반려·취소 | READ, 검토 EDIT |
| 수당 포인트 지급·정정 | 승인 요청에 명시적으로 지급하고 원본에 연결해 정정 | READ, 지급 ADD, 정정 EDIT |
| 발주·포인트 감사 기록 | 실제 대상·변경자·시각·알림 상태 확인 | READ |
| 서비스 운영자·지원·정책 | 운영자·지원 연락처·세 언어 정책과 버전 관리 | READ, 저장 EDIT |

고객은 본인에게 안내된 상품, 본인 요청과 포인트를 조회한다. 다른 회원 번호를 사용해 상품·요청·원장을 열 수 없다. 잘못된 권한이나 다른 쇼핑몰 접근을 발견하면 해당 동작을 멈추고 계정 권한을 확인한다.

## 상품 준비와 고객 발주 안내

1. 사용할 권리가 있는 상품 정보와 이미지 출처를 확인한다. 수집 상품은 지원되는 출처의 파싱 결과를 검토하고, 실제 확인한 값만 네이티브 상품으로 등록한다. 차단·누락·다중 옵션을 임의 값으로 채우지 않는다. 승인된 실제 샘플과 합성 검사용 상품을 구분한다.
2. **상품 발주 안내**에서 활성 회원 번호, 네이티브 상품 번호와 정확한 옵션 번호를 선택한다. 옵션 없는 상품은 0이다. 화면의 최근 회원·상품·옵션 목록을 참고하고 같은 쇼핑몰 소속인지 다시 확인한다. 상품은 비활성·숨김·주문 불가 상태를 유지할 수 있다.
3. 기본 수량과 최대 수량, 고객에게 보일 안내를 입력한다. 기한은 선택 사항이며 화면에 표시한 UTC 기준으로 입력한다. 직접 등록 상품 이미지를 공개하려면 해당 상품의 이미지 번호와 사용 권리 근거를 확인한다. 승인되지 않은 이미지는 표시하지 않는다.
4. **상품 발주 안내 보내기**를 누르고 목록의 대상·상품·옵션·수량·기한을 다시 확인한다. 고객은 본인 화면에서 수량과 확인 요약을 보고 명시적으로 요청한다. 안내 1건당 요청은 1건이다.
5. 제출 전 안내를 회수하려면 사유와 함께 **제출 전 안내 회수**를 사용한다. 회수·만료·오래된 버전의 화면으로는 새 요청을 제출할 수 없다. 제출된 상품·옵션·수량·안내 스냅샷은 유지된다.

상품의 가격이 있으면 참고 정보로 다룬다. 발주 요청은 외부 쇼핑몰 구매나 결제를 실행하지 않는다. 고객별 업무 접근을 위해 과거 판매자 승인 또는 상품 판매 설정을 켜지 않는다.

## 요청 수동 검토와 별도 포인트 지급

1. **발주 요청 검토**에서 요청 번호, 고객, 상품·옵션과 수량을 확인한다. 미결 요청에 고객이 볼 사유를 입력해 승인·반려·취소한다. 최종 결정은 한 번이며 다시 승인 상태로 되돌리지 않는다. 상품·수량을 다시 안내해야 하면 새 안내를 만든다.
2. 승인 후 **수당 포인트 지급·정정 → 승인 · 포인트 지급 대기**에서 같은 요청과 고객을 다시 확인한다. 승인은 포인트를 생성하지 않는다.
3. 양의 정수 포인트와 지급 사유를 입력하고 **승인 요청에 포인트 수동 지급**을 누른다. 상품 가격에 따른 자동 계산이나 기존 주문·입금의 자동 적립은 없다. 같은 승인 요청에는 기본 지급 한 번만 저장된다.
4. 지급 내역에서 회원의 **원장 조회**를 열어 잔액·원장·사유를 다시 읽는다. 고객도 새 로그인에서 본인 잔액과 내역을 확인한다. 재시도·동시 운영자·다른 요청 키로 같은 요청을 중복 지급하지 않는다.
5. 오지급은 원본 지급의 **원본 지급에 연결하여 정정**을 사용한다. 예시 합성값 `+100P → -20P = 80P`처럼 사유와 signed 정정 원장을 추가한다. 정정 후 원본 지급의 순합계는 0 이상, 원본 금액 이하이며, 이전 차감을 복구하는 양의 정정도 그 범위에서 허용한다. 원본 원장을 수정·삭제하지 않는다.

잔액은 수당 포인트 기록이다. 현금·출금 가능액·송금 완료로 표시하거나 별도 외부 처리 때문에 자동 차감하지 않는다. 원장 합계와 잔액이 다르면 신규 지급·정정이 차단되고 운영 감사 이벤트가 남는다. 재지급으로 맞추지 말고 담당자가 무결성과 동일 복구 시점을 조사한다.

## 실제 운영자·고객 지원·정책 설정

**서비스 운영자·지원·정책**에서 `operator_name`, `support_email`, 선택 사항인 `support_phone`·`support_url`, 일본어·영어·한국어의 서비스 이용약관(`terms`)·개인정보 처리방침(`privacy`)·수당 포인트 정책(`points`)을 입력한다. 지원 URL은 인증 정보 없는 HTTPS 주소다.

저장은 새 버전과 변경자·시각을 남긴다. 실제 운영자 이름, 지원 이메일과 세 언어의 세 정책이 모두 입력되면 고객 공개 링크가 표시된다. 화면에 “입력 필요”가 있으면 해당 공개 준비가 완료되지 않은 상태다. 정책 문구의 법적 승인이나 사업 사실을 시스템이 대신 확인하지 않는다.

LOGISTEED 기업 개요 등 회사 참조정보는 실제 서비스 운영자 신원·소속·운영 권한의 증거가 아니다. 해당 정보에서 운영자 이름이나 고객 지원 연락처를 추정하지 않는다. 지급 기준·정정·이의 문의·보존기간과 개인정보 처리는 실제 운영 책임자가 승인한다. 필요한 외부 값과 차단되는 작업은 [운영 입력 체크리스트](PRODUCTION_DEPLOYMENT.md#현재-서비스의-운영-입력-체크리스트)에 모은다.

## 고객 알림과 비공개 worker

상품 안내·회수, 요청 접수·검토, 수당 포인트 지급·정정은 transaction 안에서 인앱 알림을 기록한다. 메일과 Push는 commit 후 별도 채널 상태로 처리한다. 외부 전달 실패가 포인트를 다시 지급하거나 인앱 알림을 없애지 않는다. 네이티브 비밀번호 재설정 메일은 계속 사용한다.

운영 서버 담당자는 실제 쇼핑몰 번호와 명시적 채널을 사용해 다음 private CLI를 스케줄러에서 실행한다. 웹 URL로 dispatch하지 않는다.

```sh
php modules/ordenowaprocurement/bin/dispatch-notifications.php --shop=1 --channels=mail,push --limit=25
```

명령 예시의 1은 실제 확인한 쇼핑몰 번호로 바꾼다. 일반 실행 간격은 1분이며 스케줄러 등록은 환경 담당자가 수행한다. 메일은 전송 시점의 동일 쇼핑몰 활성 고객 이메일과 고객 언어를 조회해 세 언어 전용 템플릿으로 보낸다. 본문에는 일반 안내와 해당 워크스페이스 로그인 링크만 포함하고 포인트 금액·잔액·상품 스냅샷을 포함하지 않는다.

채널별 확정 실패는 60·120·240·480초 후 최대 5회까지 시도한다. 완료된 전달은 반복하지 않는다. 전송 중 process가 종료되거나 결과가 불확실하면 `UNCERTAIN`으로 기록하며 자동 재전송하지 않는다. 담당자가 실제 전송 기록을 조사한 뒤 가능한 중복 전달을 명시적으로 수락할 때만 다음 명령을 사용한다. 시도 횟수는 유지된다.

```sh
php modules/ordenowaprocurement/bin/dispatch-notifications.php --shop=1 --channels=mail --retry-uncertain=DELIVERY_ID --ack-possible-duplicate --limit=25
```

`FAILED`와 `UNCERTAIN`은 조사 대상이다. 고객 주소·구독 endpoint·비밀키·메일 원문·잔액을 일반 로그나 이슈에 넣지 않는다. 상세 동작은 [worker 안내](../modules/ordenowaprocurement/bin/NOTIFICATIONS.md), Web Push의 실제 활성 조건은 [운영 배포 준비](PRODUCTION_DEPLOYMENT.md#web-push-활성-조건)에서 확인한다.

## 백업·지원과 검증 범위

발주 안내·요청·스냅샷·검토·포인트 지급·원장·계정·정책·감사·알림 및 채널 상태를 같은 복구 시점으로 보존한다. 복원 후 소유권, 최종 검토, 요청별 기본 지급 한 번과 `SUM(ledger.delta)=balance`를 확인한다. 외부 전달 이력이 불확실한 복구본에서 worker를 자동 재가동하지 않는다.

현재 기능별 격리 검사 결과를 운영 복원·실제 SMTP·실제 기기 Push·전체 관리자 한국어·PC/모바일 시각 QA의 완료로 확대하지 않는다. 지원 요청에는 기능·시각·실행 ID·재현 단계와 개인정보를 제거한 상태만 기록한다. 운영 배포와 복원은 [운영 runbook](PRODUCTION_DEPLOYMENT.md)의 실제 담당자·환경·승인값을 준비한 뒤 진행한다.

## 보관자료 — 이전 판매·배송 관리자 안내

아래는 이전 소매 상거래 설계와 당시 QA를 보존한 참고자료다. 현재 상품 발주·수당 포인트의 운영 절차나 출시 입력으로 적용하지 않는다. 특히 판매가격·세금·배송비·반품·환불·은행 메뉴의 요구는 현 플랫폼 입력을 추가하지 않으며, 기존 데이터 보존·과거 회귀 조사에서만 참조한다.

### ORDENOWA 관리자 기본 운영 안내

이 문서는 이 안내에 적힌 관리자 화면의 사용 방법과 운영 전 제한을 정리한다. 관리자 전체 화면의 한국어 번역 완성을 뜻하지 않는다. 운영자에게 전달할 실제 회사정보, 상품정보, 세무 설정 또는 정책을 대신 작성하지 않는다.

#### 관리자 언어와 계정

- PrestaShop 고객용 기본 언어는 일본어다. 관리자 `admin_` 경로는 한국어를 요청하도록 구성되어 있다.
- 최초 설치 계정 외 직원을 추가할 때는 개별 접근 권한과 담당자 소유 계정을 설정한다. 계정을 공유하지 않는다.
- 주문·고객·결제 자료를 볼 권한은 실제 역할에 필요한 범위만 부여한다.

#### 상품 초안 등록·수정

1. 관리자에서 **상점 설정 → 상품 등록·관리**를 연다.
2. 일본어·영어·한국어 상품명과 설명, JPY 판매가격, 명시적인 세금 규칙, 카테고리, 옵션 및 수량을 입력한다.
3. 실제 상품을 사용할 권리가 있는 이미지(JPEG/PNG/WEBP, 이미지당 10 MB 이하, 최대 5장)를 업로드한다.
4. 저장한 뒤 편집 화면에서 가격·번역·카테고리·옵션별 재고·이미지를 다시 확인한다.

이 관리자는 PrestaShop 네이티브 상품으로 내용을 저장한다. 이 화면에서 만든 상품은 기본적으로 비활성·숨김·주문 불가 상태로 저장되며, 이 화면에는 판매 공개 승인 기능이 없다. 상품 출처, 이미지 사용권, 재고, 가격 및 세무 검토가 끝나기 전에는 다른 설정으로 판매를 열지 않는다. 영어·한국어 입력이 비어 있으면 일본어 값으로 대체되므로 해당 언어로 상품 정보를 제공하려면 값을 직접 입력한다.

#### 사업자·브랜드·SEO·PWA 설정

1. **쇼핑몰 운영 설정** 메뉴의 **사업자 정보**, **브랜드·로고**, 고객센터, 배송·환불 안내, SEO 및 PWA 항목을 수정한다.
2. 브랜드·로고 항목에는 ZIP이 아니라 승인된 원본 로고, 파비콘 심벌, PWA 아이콘을 각각 업로드한다. 저장 후 PC·모바일·관리자·이메일·favicon·PWA·OG 파생 미리보기를 확인한다.
3. 승인된 회사·정책 문구와 브랜드 자산을 미리보기한 뒤 게시한다.
4. 변경 이력에서 버전, 변경자 ID, 변경 시각, 초안/게시 중 상태를 확인한다. 일반 설정에서 이전 버전을 초안으로 복원할 수 있지만 은행 계좌나 은행이체 연결 정보가 포함된 차이가 있으면 이 복원은 거부된다. 은행 계좌 변경·이력 복원은 별도의 **은행 계좌** 메뉴에서 처리한다.

게시 기능은 입력한 정보의 사실성이나 법적 승인 여부를 확인하지 않는다. 판매자 법적 정보, 지원 연락처, 배송·환불·개인정보 문구와 자산 사용권을 승인받은 뒤 게시한다. KURANEA 원본은 백업으로 보존한다.

#### 배송 및 주문

- 출시 가격 정책은 일본 지원 배송지역의 고객 배송비 ¥0이다. 실제 carrier 계약, 배송 가능 지역 및 판매자 부담 비용은 운영자가 별도로 확인한다.
- 주문 메뉴에서 고객 주소, 상품, 수량, 배송비, 세금 및 총액을 확인한다. 주문 상세의 상태 양식으로 PrestaShop 상태를 변경할 수 있다.
- 취소 전 결제 모듈과 실제 결제 여부를 확인한다. 미결제 주문 취소는 결제를 취소하거나 환불하지 않는다.
- 반품 승인과 credit slip 생성은 PrestaShop의 별도 흐름이다. credit slip은 외부 결제 제공자의 현금 환불 완료를 뜻하지 않는다.
- 주문 취소·반품·환불 사유와 고객 통지는 판매자가 확정한 운영 정책에 따라 처리한다.

GitHub Actions의 주문 상태 검사는 실행 ID가 붙은 합성 `ps_checkpayment` 미결제 주문만 취소한다. 반품·credit slip 검사는 테스트 전용 상태의 합성 주문을 사용하며 실제 결제 제공자 호출이나 송금·현금 환불은 하지 않는다.

#### 백업 및 복원

GitHub Actions의 복원 drill은 실행 전용 DB와 named volume 사본을 별도 임시 프로젝트에 복구하는 QA다. 이 artifact를 운영 백업으로 사용하지 않는다. 운영 백업 위치·암호화·보존기간·접근자·복원 승인·RPO/RTO가 정해지고 별도의 운영 runbook 및 drill이 검증되기 전에는 복원 가능하다고 간주하지 않는다.

#### 지원 요청 전 확인할 자료

결함 보고에는 비밀값이나 고객 개인정보를 넣지 말고, 화면/기능, 시간대, 실행 ID, 재현 단계 및 마스킹된 상태를 기록한다. 판매자·상품·세금·배송·결제·환불 정책의 입력은 저장소 담당자가 임의로 추정하지 않는다.
