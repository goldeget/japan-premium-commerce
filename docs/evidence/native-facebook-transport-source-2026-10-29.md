# Facebook transport failure branch: pinned source facts

## Read-only source evidence

- The target runtime readback is documented by the existing isolated native-boundary evidence: `ps_facebook` is installed, active, version `1.38.19`; the matching upstream release is PrestaShopCorp/ps_facebook tag `v1.38.19` (commit `f4b63c967f4d898cecabd8e234a4c5df5bffe21a`). The test helper still reads and validates the installed `config.xml` at runtime; it does not trust this note as runtime inventory.
- The pinned upstream [Facebook legacy controller](https://github.com/PrestaShopCorp/ps_facebook/blob/v1.38.19/controllers/admin/AdminPsfacebookModuleController.php) calls `PsAccountsInstaller\\Installer\\Installer(...)->install()` near the start of `initContent()`, then later calls `BillingAdapter::getCurrentSubscription()`. The production controller action must therefore not be invoked to manufacture a transport failure.
- The pinned [BillingAdapter](https://github.com/PrestaShopCorp/ps_facebook/blob/v1.38.19/classes/Adapter/BillingAdapter.php) constructs `PrestaShop\\Module\\PrestashopFacebook\\Http\\HttpClient` against `https://billing-api.distribution.prestashop.net/v1/` and calls `get()` for the subscription endpoint.
- The pinned [HttpClient](https://github.com/PrestaShopCorp/ps_facebook/blob/v1.38.19/classes/Http/HttpClient.php) has a public `__construct(string $baseUrl = '')`, `get(string $url, array $params = [])`, and `request(string $method, string $url, $data = null)`. `request()` throws a global `RuntimeException` when `curl_exec()` returns `false`, with message format `cURL error (<errno>): <curl error>`. The exception's file is this installed `HttpClient.php`; the call trace includes the actual class and `get`/`request` frame. The helper validates reflection path and runtime trace against the installed module file before accepting a 503.
- PrestaShop 9.2.0 [LegacyRouterChecker](https://github.com/PrestaShop/PrestaShop/blob/9.2.0/src/PrestaShopBundle/Routing/LegacyRouterChecker.php) resolves the `controller=AdminPsfacebookModule` query, instantiates and initializes its native module controller, then writes the trusted request attributes `_legacy_controller_class`, `_legacy_controller_name`, `_legacy_controller_action`, `_legacy_controller_instance`, and `_legacy_controller_is_module`. The expected native route is `admin_legacy_controller_route` and the Symfony action is `PrestaShopBundle\\Controller\\Admin\\LegacyController::legacyPageAction`.
- PrestaShop 9.2.0 [LegacyController](https://github.com/PrestaShop/PrestaShop/blob/9.2.0/src/PrestaShopBundle/Controller/Admin/LegacyController.php) checks the native permission with the action and controller grant subject before dispatching the legacy action. For this page the helper independently requires `IS_AUTHENTICATED_FULLY` and `read` on `AdminPsfacebookModule`; it never accepts the legacy anonymous-controller path.
- PrestaShop 9.2.0 locks Symfony SecurityBundle v6.4.45 (source commit `de06cd0f756ca8fe4894c7e95bac71d90bb94e64`). Its pinned [`security.php`](https://github.com/symfony/security-bundle/blob/de06cd0f756ca8fe4894c7e95bac71d90bb94e64/Resources/config/security.php) defines `security.helper` as `Symfony\\Bundle\\SecurityBundle\\Security` and aliases the class to that service without making the private helper directly fetchable from the compiled container. The project subscriber receives it through normal constructor injection. The isolated test reads the same subscriber instance from the exception listener list and uses a boolean-only test bridge; it never calls `$container->get('security.helper')` and never fabricates a token. Symfony FrameworkBundle v6.4.46 also defines `request_stack` as public; the response-time CSRF probe verifies the event request is the currently stacked main request.
- The native admin error page can use the same [standard admin layout](https://github.com/PrestaShop/PrestaShop/blob/9.2.0/src/PrestaShopBundle/Resources/views/Admin/layout.html.twig) used by the installed MBO error template ([pinned template](https://github.com/PrestaShopCorp/ps_mbo/blob/v5.3.2/views/templates/admin/error.html.twig)). The fallback uses a project-owned template with fixed Korean copy and does not expose exception text, URL, response body, or credentials.

## Safe failure injection design

The authenticated BrowserKit request uses the real native login form and a link generated by PrestaShop's own `Link::getAdminLink()`. A test-only `kernel.controller` listener runs after the native context listeners and before the legacy controller action. It verifies the exact Facebook route, controller instance/class, module metadata, active-module inventory, authenticated user, and native READ grant. For the positive case only, it reserves a per-run IPv4 loopback ephemeral port using `stream_socket_server(..., STREAM_SERVER_BIND)` without `STREAM_SERVER_LISTEN`, keeps that bind open, disables proxy environment variables for the test process, and invokes the installed `HttpClient` with an HTTPS base URL at that loopback address. The actual cURL client therefore fails at loopback connect before TLS or HTTP and emits its real installed-source `RuntimeException`; it cannot connect to a remote host.

The listener throws before `LegacyController::legacyPageAction()` enters `initController()` or calls `AdminPsfacebookModuleController::initContent()`. Thus the test does not run `PsAccountsInstaller`, `BillingAdapter`, or other Facebook module initialization work. Other modes inject only a generic runtime failure, an access-denied exception, or a generic failure on a different authenticated route to prove the fallback declines them.

The Symfony kernel/configuration bootstrap and genuine login may perform their normal database/session/audit work. Those bootstrap effects are not instrumented. The test records that fact and only claims that its explicitly injected HTTP request is loopback-only, its test listener avoids the Facebook vendor action, and it makes no application business-data mutations.
