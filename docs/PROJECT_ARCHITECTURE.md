# ORDENOWA — 상품 발주 요청·수동 검토·포인트 플랫폼

2026-10-29 한국시간 최신 사용자 정의를 적용한다. 운영자가 고객에게 특정 상품의 발주를 안내하면, 고객은 쇼핑몰에서 물건을 주문하듯 해당 상품을 확인하고 발주 요청한다. 운영자는 요청을 수동 검토한 뒤 고객의 포인트 잔액에 수당을 반영한다.

[최종 상세 아키텍처](superpowers/specs/2026-10-29-ordenowa-procurement-points-platform-design.md)가 현재 설계 기준이다. 문서 작성과 실제 기능 구현·검증·출시 완료는 구분한다.

## 확정된 흐름

1. 운영자가 상품을 등록하거나 선택하고 고객에게 ‘이 상품을 발주 요청하세요’라고 안내한다.
2. 고객은 자신에게 안내된 상품의 카드·상세·수량·요청 확인 화면을 거쳐 발주 요청한다.
3. 운영자가 요청을 수동 승인하거나 사유와 함께 반려한다. 고객은 자신의 요청 내역에서 결과를 확인한다.
4. 승인 요청에 대해 지급 권한이 있는 운영자가 포인트를 입력하고 별도 지급 버튼으로 반영한다. 승인만으로 자동 적립하지 않는다.
5. 고객은 본인 포인트 잔액과 적립·정정 내역만 조회한다. 별도 처리는 운영자가 맡으며, 플랫폼은 이를 현금 송금 완료로 표시하거나 자동 차감하지 않는다.

상품 카드·상세·요청 확인 화면은 익숙한 쇼핑형 화면으로 제공한다. 일반 작업 결과나 증거를 제출하는 업무관리 시스템으로 확장하지 않는다. 판매 결제, 배송지·운송장·배송·반품·상품 환불, 포인트 충전·사용·양도·현금 환산·고객 출금 기능은 현재 범위에 없다. 수동 수당 포인트는 필수 기능이다.

## 기술 및 데이터

기존 PrestaShop 9.2.0, Hummingbird 2.1.2, MariaDB 10.11과 상품·회원·관리자·브랜드·언어·문의·보안 기능을 재사용한다. 코어와 부모 테마는 수정하지 않는다.

새 `ordenowaprocurement` 모듈에서 고객별 상품 안내, 발주 요청, 검토, 포인트 원장, 감사 이력과 알림을 관리한다. 기존 주문·결제·입금 확인 테이블을 이름만 바꿔 쓰지 않는다.

실제 전용 InnoDB 테이블은 `assignment`, `request`, `review`, `point_account`, `point_award`, `point_ledger`, `activity`, `notification`, `notification_delivery`, `policy`, `support_link`, `support_post`의12개다. 설치 prefix를 적용하고 native 고객·직원·상품·문의와 명시적 adapter로 연결한다. [저장소 스키마](../modules/ordenowaprocurement/src/Infrastructure/Schema.php)와 [최신 검증 결과](TEST_RESULTS.md)가 구현 기준이다.

초기 설계는 안내된 상품 한 개당 발주 요청 한 건, 승인 요청당 기본 포인트 지급 한 번이다. 원장·잔액·지급 기록·감사·알림 대기를 한 DB 트랜잭션으로 저장한다. DB 고유 제약과 잠금, 재시도 식별자로 이중 요청·동시 지급을 막는다. 정정은 원본 지급을 참조하는 새 기록을 추가하며 기존 원장을 덮어쓰지 않는다.

회원·발주 요청 접근은 `WorkspaceAccessPolicy`로 기존 판매자 승인 게이트와 분리한다. 비공개 상품을 보여주려고 판매·checkout 플래그를 켜지 않는다. 고객에게 허용된 상품만 전용 화면에서 표시한다. 기존 상거래 메뉴와 직접 접근 경로는 비활성화하고 과거 코드·데이터는 보존한다.

## 운영·개인정보·출시

ORDENOWA/オーデノワ/오데노와와 승인된 로고·자산은 유지한다. KURANEA 기술 경로와 과거 원본도 보존한다. LOGISTEED 참고정보는 실제 운영 주체나 권한의 증거가 아니다. 운영자·고객지원·발주 요청·포인트·개인정보 정책은 과거 판매자·배송·환불 정책 검증과 분리한다.

고객 일본어 기본 및 영어·한국어, 운영에 노출되는 전체 관리자 화면의 한국어 요구를 유지한다. 상품 배정·요청·검토·포인트·문의는 고객 소유권과 관리자 역할로 보호한다. 비공개 응답은 저장 캐시와 검색엔진 색인에서 제외한다. 새 화면에서 접근성·성능·PWA·알림을 검증한다.

[현재 출시 요구사항표](RELEASE_REQUIREMENTS_MATRIX.md)의 상품 안내 → 고객 요청 → 운영자 검토 → 수동 지급 → 고객 새 로그인 조회가 핵심 인수 흐름이다. 고객 간 접근 차단, 중복·동시 지급, 정정, 재시작·백업 복구도 통과해야 한다. 이전 쇼핑몰 QA는 당시 범위의 역사적 증거로 보존한다.

전용 발주 안내·요청·수동 검토·포인트 원장·정정·감사·알림과 native 연결은 구현됐고 격리 MariaDB 집중 검사를 통과했다. 실제 로컬 native 설치에서 발주/수동100→80P·격리·메일·복원과 품질 검증을 통과했다. 검증 코드91c6098의 전체#40763074207은38/38phase·aggregate·cleanup SUCCESS이며, 새 hosted20target의 독립 실제 시각 검수도 완료했다. 실제 상품 원문·운영 설정·실기기 인수는 남는다. 정확한 코드·결과·범위는 TEST_RESULTS.md를 따른다. 배송·반품·환불 자료 대기를 출시 차단 사유로 유지하지 않는다. `main`, 기존 사용자 파일, 운영 DB·volume을 보존하고 변경은 `work`에 저장한다. 이 문서는 배포나 실거래 실행 지시가 아니다.

## 상품 파싱·분류 연결 (후속 사용자 지시 적용)

Amazon Japan·Rakuten 상품의 제목·수집 시점 JPY 참고 가격·상세 설명·사진 후보·원본 카테고리 경로 수집은 필수 범위다. 기존 `kuraneacatalog` 수집→검수→동일 native 상품 등록 흐름을 재사용한다. JSON-LD와 지원 HTML 구조를 구분하며, 추천 상품·모호한 옵션/가격·차단/인증 페이지를 성공 상품으로 저장하지 않는다. 원문은 출처와 checksum으로 연결하고 이미지는 공개 사용 근거를 검토한 로컬 이미지로 게시한다.

검수자가 승인한 native 카테고리·하위 카테고리를 배정 snapshot에 보존한다. 고객 메뉴와 필터는 본인에게 배정된 상품의 카테고리만 표시한다. 원본 카테고리와 플랫폼 카테고리 매핑은 검토 없이 임의로 확정하지 않는다. 실제 원문 호환, 합성 fixture 검사, native 저장·재조회, 시각 검수는 서로 다른 근거다. 현재 클라우드의 실제 쇼핑몰 HTTPS 접근은 관리 네트워크 CONNECT403으로 차단돼 있어 실제 전 상품 수집이나 운영 상품 게시 완료를 주장하지 않는다.
